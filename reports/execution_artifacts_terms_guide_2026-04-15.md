# Execution Artifact Terms Guide

Date: 2026-04-15
Scope: Terms present in execution artifact files generated by one pipeline run:
- run_results/*.notes.jsonl
- run_results/*.summary.json

Audience: Beginner

How to read paths in this document:
- Dot paths represent nested JSON fields.
- If a field is a list, examples like .0, .1 in raw files just mean list item positions.

## 1. Notes File Terms

Notes artifact shape:
- One JSON object per processed note.
- File extension: .notes.jsonl

### 1.1 Top-level fields in each note record

| Term | General meaning | Project-specific meaning |
|---|---|---|
| run_id | Unique identifier for one execution run. | Groups all notes and summary outputs for the same pipeline execution. |
| ts_utc | Timestamp in UTC. | Time when this note record was written. |
| note_index | Zero-based note counter. | Processing order of this note inside the run. |
| note_id | Business identifier of an item. | Clinical note identifier from dataset service. |
| split | Data partition label. | train, val, or test split assigned by split logic. |
| group_id | Group identifier. | Rollout grouping key used for GRPO-like training semantics. |
| inputs | Input payload section. | Sanitized input metadata for note text and ground truth codes. |
| rewriter | Rewriter step output section. | Request/response metadata and latency for rewrite service call. |
| icd10 | ICD coding step section. | Request/response metadata and latency for ICD service call. |
| reward | Reward step section. | Reward request/response and latency for val/test (and metadata for train behavior). |
| metrics | Evaluation metrics section. | Per-note quality metrics (for example enhanced vs GT precision/recall/F1). |
| status | Processing status. | ok for successful note execution, error on failure. |
| error | Error field. | Failure text when status is error; null when successful. |
| timing | Timing section. | End-to-end note-level duration values. |

### 1.2 inputs fields

| Term | General meaning | Project-specific meaning |
|---|---|---|
| inputs.clinical_note.sha1 | Hash digest of text. | Privacy-preserving identifier for the original note content. |
| inputs.clinical_note.len | Character length. | Size of original clinical note used for processing diagnostics. |
| inputs.gt_codes | Ground-truth labels list. | ICD-10 targets associated with the note from dataset service. |

### 1.3 rewriter fields

| Term | General meaning | Project-specific meaning |
|---|---|---|
| rewriter.request_meta.note_id | Request identity field. | Note id sent to rewriter service. |
| rewriter.request_meta.clinical_note_sha1 | Input hash. | Hash of note text sent to rewriter, avoids storing raw text. |
| rewriter.request_meta.clinical_note_len | Input size. | Note length used for model behavior and latency interpretation. |
| rewriter.response_meta.rewritten_prompt_sha1 | Output hash. | Hash of rewritten prompt produced by rewriter service. |
| rewriter.response_meta.rewritten_prompt_len | Output size. | Length of rewritten prompt text. |
| rewriter.response_meta.generation_source | Provenance label. | Indicates rewrite source path such as model_first, guided_fallback, rule fallback, cache path. |
| rewriter.response_meta.log_prob_old | Policy log probability scalar. | Behavior policy likelihood used later by RL components. |
| rewriter.response_meta.value_estimate | Value prediction scalar. | Baseline value estimate associated with generated action. |
| rewriter.timing_sec | Latency in seconds. | Time spent on rewrite service call for this note. |

| Term | General meaning | Project-specific meaning |

### 1.5 reward fields

| Term | General meaning | Project-specific meaning |
|---|---|---|

| reward.response.metrics.components_enh.P_card | Penalty component. | Cardinality mismatch penalty for enhanced branch. |
| reward.response.metrics.components_org.D_set | Distance component. | Set-distance contribution for original branch. |
| reward.response.metrics.components_org.P_cov | Penalty component. | Coverage/missing-code penalty for original branch. |
| reward.response.metrics.components_org.P_extra | Penalty component. | Extra-code penalty for original branch. |
| reward.response.metrics.components_org.P_card | Penalty component. | Cardinality mismatch penalty for original branch. |
| reward.response.metrics.diagnostics.worst_gt_coverage_code | Diagnostic code label. | GT code with weakest coverage against predictions. |
| reward.response.metrics.diagnostics.worst_pred_match_code | Diagnostic code label. | Predicted code with weakest match to GT set. |
| reward.timing_sec | Latency in seconds. | Time spent in reward service call for this note. |

### 1.6 timing and quality fields

| Term | General meaning | Project-specific meaning |
|---|---|---|
| timing.note_total_sec | End-to-end duration. | Total wall-clock time to process this note across pipeline steps. |

## 2. Summary File Terms

Summary artifact shape:
- One JSON object per run.
- File extension: .summary.json

### 2.1 Run identity and volume

| Term | General meaning | Project-specific meaning |
|---|---|---|
| run_id | Unique execution id. | Same id shared by notes and summary artifacts for one run. |
| started_at_utc | Start timestamp. | Run start time in UTC. |
| finished_at_utc | End timestamp. | Run completion time in UTC. |
| total_target | Planned item count. | Number of notes targeted by this execution (for example max-notes). |
| total_processed | Actual processed count. | Number of note records completed and written. |
| failures | Failure count. | Count of notes that ended in status error. |
| elapsed_hr | Total runtime in hours. | End-to-end run duration measured by orchestrator. |

### 2.2 Split-level counters

| Term | General meaning | Project-specific meaning |
|---|---|---|
| train_success | Success counter. | Number of successful train-split notes. |
| val_success | Success counter. | Number of successful validation-split notes. |
| test_success | Success counter. | Number of successful test-split notes. |

### 2.3 Parse and comparability quality

| Term | General meaning | Project-specific meaning |
|---|---|---|
| parse_success_rate | Fraction metric. | Share of notes with parsing_success true from ICD response. |
| both_parse_success_rate | Fraction metric. | Share of notes where both enhanced and original parsing succeeded. |
| original_parse_failure_rate | Fraction metric. | Share of notes where original branch parse failed. |
| train_comparability_failure_count | Count metric. | Train notes where both-parse comparability requirement was not met. |
| parse_failure_taxonomy | Diagnostic object. | Aggregate parse-failure categories copied from ICD observability. |

## 3. Beginner Interpretation Tips

1. Use status and failures first.
- If notes status is mostly ok and summary failures is 0, the run processed data successfully.

2. Use parse and reward quality together.
- both_parse_success_rate tells you whether branch comparisons are fair.
- test_reward_mean and val_reward_mean tell you if enhanced prompts are helping on average.

3. Use timing percentiles to detect bottlenecks.
- p95 and p99 show tail latency pain points better than median alone.

4. Use observability to separate model errors from transport errors.
- ICD observability highlights parse problems.
- Reward observability and rollout metrics highlight queue/transport issues.

5. Trust summary for run-level health and notes for root-cause details.
- Summary gives aggregates.
- Notes JSONL gives per-note forensics.
